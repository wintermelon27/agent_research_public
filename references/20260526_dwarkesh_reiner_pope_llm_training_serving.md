## 一、批处理的经济学：快速模式为什么能加速？

### 1.1 问题的起点
多家模型公司（Claude/Cursor/GPT）提供"快速模式"（Fast Generation）：
- 付 **6 倍价格** → 获得 **约 2.5 倍速度** 的流氏输出

主持人的三个问题：
1. **为什么多付钱就能更快的延迟？**
2. **能不能持续往上加**（付 100 倍获得更快）？
3. **反过来行不行**（慢速便宜模式）？

### 1.2 批处理是关键
Reiner 给出了他印象最深的一句话：

> *"如果你不把很多用户合在一起做批处理，你得到的成本和经济效益可能会比批处理时差上 **千倍**。"*

核心原因：单个用户的权重读取成本无法被分摊。批处理让多个用户**共享一次权重加载**，均摊后成本骤降。

### 1.3 快速模式的上限
但加速存在天然瓶颈——存在一个**延迟下限**，即使付 100 倍的钱也无法突破。这个下限来自：无论批次多大，总要把全部模型参数从内存读入芯片，而这需要一定时间（由内存带宽决定）。

快速模式本质 = 增大批次大小，更充分地利用算力；但 2.5x 而非 6x 的加速比说明**边际收益递减**。

## 二、Roofline 模型：延迟的双约束线

Reiner 用简化的 Roofline 分析（两个时间约束）来量化延迟问题：

### 2.1 两个时间分量

**① 计算时间（Compute Time）**
$$T_{compute} = \frac{B \times N_{active}}{F_{peak}}$$

- $B$ = 批次大小（Batch Size）
- $N_{active}$ = 活跃参数数量（每个Token实际参与计算的参数量）
- $F_{peak}$ = 芯片峰值算力（ FLOPS）
- **特性**：随批次大小线性增长，无截距

**② 内存访问时间（Memory Time）**
$$T_{memory} = \underbrace{\frac{N_{total}}{M_{bandwidth}}}_{常数\ 基准项（权重加载）} + \underbrace{\frac{B \times L \times S}{M_{bandwidth}}}_{KV缓存读取}$$

- $N_{total}$ = 总参数量
- $L$ = 上下文长度
- $S$ = 每 Token 字节数（模型参数）
- $B \times L \times S$ = KV 缓存总量，随批次大小和上下文长度线性增长

### 2.2 最终延迟 = max(计算时间, 内存时间)

两条曲线取包络线（max），形状如下：
- **批次小时**：内存时间主导（存在固定基准截距，即权重读取）
- **批次足够大后**：计算时间主导（线性增长，超过内存曲线）

**关键洞察：存在延迟下限**
- 当批次很小时，延迟趋于一个**常数下限** = $\frac{N_{total}}{M_{bandwidth}}$
- 即便付 100 倍的钱，你也快不过这条线——这是物理限制，不是工程问题

### 2.3 上下文长度改变约束结构
当上下文长度增加时，KV 缓存读取项上升，导致内存曲线变陡，可能**从计算受限转变为内存受限**。

两种注意力机制的扩展性差异：
- **稠密注意力（Dense Attention）**：KV 缓存读取随上下文长度线性增长 → 容易内存受限
- **稀疏注意力（Sliding Window / MoE）**：扩展性好得多

这直接回答了"为什么上下文长度不是越长越好"——超过最优长度后，算力利用率会骤降（最优长度 10 万 Token → 拉到 20 万，算力利用率降到 50%）。

## 三、成本分析：每个 Token 的成本曲线

### 3.1 成本方程
成本 = GPU 时间 × 每小时租金（$/GPU/hr）

GPU 时间如何随批次大小变化？把延迟方程 **除以 B**（每个 Token 成本 = 总时间 / Token 数）：

| 成本项 | 随 B 的变化 |
|--------|------------|
| 计算成本 $T_{compute} / B$ | **常数**（线性 → 常数）|
| KV 缓存读取 $/B$ | **常数**（线性 → 常数）|
| 权重读取 $/B$ | **双曲线下降**（常数/B → 急剧下降）|

### 3.2 成本曲线形状

- **B=1（单用户）**：成本近乎无穷，权重读取无法分摊
- **B 增大**：权重读取成本迅速被分摊
- **B 足够大**：成本趋近于**计算时间决定的底线**（即每个 Token 纯计算成本）

这就是为什么单用户推理成本极高，而批量 API 服务可以便宜得多。

### 3.3 最优批次大小推导

令计算时间 = 内存访问时间（平衡点）：

$$\frac{N_{total}}{M_{bandwidth}} = \frac{B \times N_{active}}{F_{peak}}$$

重新排列：

$$\frac{F_{peak}}{M_{bandwidth}} = B \times \frac{N_{active}}{N_{total}}$$

左边是**硬件常数**（算力 ÷ 内存带宽），在历代 GPU 上稳定在 **≈ 300**。

右边 = 批次大小 × **稀疏度**（活跃参数 / 总参数）。

因此：
$$\boxed{B_{optimal} \approx 300 \times sparsity}$$

以 DeepSeek MoE 为例：
- 总参数 7000 亿，活跃参数约 370 亿 → 稀疏度 ≈ 1/20
- 实际上 DeepSeek V3 的稀疏度更接近 1/8（每个 Token 从 256 个专家激活 32 个）
- 最优批次大小 ≈ **2400 个序列**（每个序列 = 一个用户请求）

**实践结论**：最优批次大小只取决于稀疏度，与模型绝对规模几乎无关。

## 四、内存墙：为什么这是真正的枷锁

### 4.1 内存墙没有真正的解决方案
Reiner 的核心断言：

> *"我认为这是因为内存墙的问题没有真正的解决方案。"*

每代硬件（从 A100 → H100），算力和内存带宽都在提升，但 **$F_{peak} / M_{bandwidth}$ 这个比率始终保持在约 300**。这意味着：
- 内存墙问题**不会随着硬件迭代自动消失**
- 即使 Blackwell 的 HBM 容量比 Hopper 大了 10-20 倍，内存墙依然存在

### 4.2 延迟下限的物理来源
$$\text{延迟下限} = \frac{\text{所有参数从内存读入芯片的时间}}{需要的时间}$$

当 HBM 带宽用满时，有：
$$T_{HBM} = \frac{\text{HBM 容量}}{\text{HBM 带宽}} \approx \frac{288GB}{20TB/s} \approx 15ms$$

这解释了为什么 20ms 是推理批次调度的一个经验法则——在这个时间内，刚好可以清空并替换整个 HBM 的内容。

### 4.3 纵向扩展 vs 横向扩展
**纵向扩展（单 rack）**：
- 限制因素：HBM 带宽 + 容量
- 一个 rack 的规模 ≈ 72 GPU（Blackwell），约 10-20TB HBM

**横向扩展（多 rack）**：
- rack 之间带宽只有 rack 内带宽的 **1/8**（NVLink vs InfiniBand/扩展网络）
- 超过一个 rack，All-to-All 通信（如 MoE 的专家并行）会成为严重瓶颈

这解释了为什么超大规模模型（如 GPT-4 级别）直到最近才能训练——需要等待足够大的单 rack 纵向扩展系统来容纳万亿参数模型 + KV 缓存。

## 五、混合专家（MoE）的硬件布局与通信

### 5.1 专家并行（Expert Parallelism）
标准做法：每个 GPU 放置固定数量的专家（如 72 GPU rack × 4 专家/GPU = 256 专家，对应 DeepSeek 的 256 专家 MoE）。

通信模式：**All-to-All**（任何 GPU 都可能需要和任何其他 GPU 通信）。

### 5.2 Rack 内 vs Rack 间的带宽鸿沟
- **Rack 内（Intra-rack）**：NVLink，两跳到交换机，带宽约 1.6-1.8TB/s（H100）
- **Rack 间（Inter-rack）**：约慢 **8 倍**（扩展网络）

这导致 MoE 层跨 rack 时，一半 Token 需要走慢速网络，成为性能瓶颈。

### 5.3 为什么 rack 规模这几年从 8 → 72 GPU？
从 Hopper（8 GPU tray）到 Blackwell rack（72 GPU）主要是**产品形态变化**（tray → rack），背后是更复杂的**物理设计**：线缆密度、背板连接器密度、供电、散热、重量限制等。线缆弯曲半径等物理约束才是真正的限制，而不是电气性能。

## 六、流水线并行（Pipeline Parallelism）：对推理和训练的影响不同

### 6.1 对推理：中性的优化
流水线化：
- **不提升也不变差**推理延迟（所有计算串行执行，总时间相同）
- **节省内存容量**（每个 GPU 不再需要存储整个模型）
- 但如果 rack 内存已经足够大（如 Blackwell 的数十 TB），流水线并行就没什么吸引力

### 6.2 对训练：更复杂
训练时需要：
1. 累积足够数量的 micro-batch
2. 一次性做完整批次的反向传播

存在**流水线气泡**（bubble）——43% 的 GPU 空转时间。

解决方案：**micro-batch 数量 = 流水线阶段数**，刚好填满气泡。

但用 micro-batch（而非 full batch）意味着权重加载无法被充分分摊，这是代价。

### 6.3 流水线并行对 KV Cache 无效
增加流水线阶段数：
- ✅ 权重内存占用下降（可继续切分）
- ❌ KV Cache 内存占用**不变**（无法跨阶段共享）

结论：**对 KV Cache 的优化只有两种方式**：
1. 在批次维度上分摊（增加 Batch Size）
2. 在注意力机制上做稀疏化（Sliding Window / MoE）

流水线并行对 KV Cache 容量问题**基本无效**——一旦权重足够小，KV Cache 就成为主要内存占用，且无法通过流水线来削减。

## 七、Scaling Law 放缓的真实原因

### 7.1 两个 Scaling 假设
- **固定时间假设（Fixed Time）**：训练时间固定，模型变大时如何扩展数据/算力
- **固定芯片假设（Fixed Chips）**：芯片数固定，模型变大时训练时间如何变化

### 7.2 为什么这几年扩展变慢？
原因不是"不能跨更多 rack 训练"（技术上可以），而是在等待**足够大的单 rack 纵向扩展系统**来容纳万亿参数模型 + KV 缓存。

时间线：
- **Hopper（2022）**：8 GPU tray，640GB 总内存 → 不足以容纳万亿参数模型
- **Blackwell（2024）**：10-20TB HBM，终于可以容纳一个 rack 内的万亿参数模型

这也是 Google 看起来一直在某些方面领先的原因之一——他们很早就部署了更大的纵向扩展系统。

## 八、训练成本 vs 推理成本：模型应该"过度训练"多少？

### 8.1 核心方程
总成本 = 训练成本 + 推理成本

想让总成本最小化，两个成本应该大致**相等**（下降曲线 + 上升曲线的极值点）。

具体分解：
- **预训练成本**：6 × $N_{active}$ × 数据量（6NDF 公式）
- **RL 训练成本**：类似，但有非效率因子（只有部分生成结果做反向传播）
- **推理成本**：2 × $N_{active}$ × 推理数据量

### 8.2 三种成本的数量级估算
假设：
- $\alpha_{RL} \approx 2-6$（RL 相对预训练的效率比）
- $f \approx 30$（推理 vs 预训练的效率比，推理利用率低很多）

最终推导：**预训练 Token 数 ≈ RL 训练 Token 数 ≈ 用户推理 Token 数**

即一个模型的预训练数据量，应该大致等于用户在使用该模型时产生的总 Token 量（用于生成回复的那部分）。

### 8.3 过度训练程度
如果用这个关系反推当前前沿模型的训练强度：

- 假设每秒 **5000 万个 Token** 的用户流量，模型存活 **2 个月**
- 推理总 Token 量 ≈ 2.6 × 10^15
- 最优预训练 Token 量 ≈ 2 × 10^13
- **实际训练 Token 量 / 最优 Token 量 ≈ 100 倍**

也就是说，当前前沿模型比"最优训练量"**过度训练了约 100 倍**。这不是浪费，而是用推理成本补贴训练成本——大模型学得更慢但更便宜，小模型学得快但用起来贵。

## 九、API 定价泄漏的技术信息

### 9.1 从 Gemini 3.1 定价反推架构

Gemini 3.1 在超过 **20 万 Token** 后价格贵 50%（$1.25/M vs $0.83/M）。

这意味着 **20 万 Token = 成本交叉点**（内存时间 = 计算时间的临界位置）。

在忽略权重项（Batch 足够大）后：

$$\text{每 Token 字节数} = \frac{N_{active} \times F_{peak}}{L \times M_{bandwidth}}$$

代入硬件常数 300、$N_{active} \approx 100B$、$L = 200K$：
→ 每 Token 约 **1.6-2KB**

这说明 Gemini 使用了**密集注意力**，在层之间共享全局上下文（每层 KV Cache 不独立复制）。

### 9.2 Pre-fill vs Decode 的 5 倍差价
API 中 **Output 贵 5 倍**的原因：
- **Decode（生成）**：每步只处理 1 个 Token，主要受限于**内存带宽**（需要读取整个模型权重）
- **Pre-fill（输入处理）**：一次处理数千个 Token，计算强度高但**计算受限**，可充分并行

5 倍定价差异说明：模型服务严重受限于**内存带宽**，而非算力。

### 9.3 缓存命中便宜 10 倍的真相
从成本结构看：
- **重新计算**：GPU 时间 × 算力成本（贵）
- **从 HBM 读取**：每 Token 字节数 / HBM 带宽（便宜）

缓存命中 = 直接从 HBM 读，已计算过的 KV Cache 不需要重新执行前向传播 → 成本是重新计算的约 1/10。

## 十、多层内存经济学：从 HBM 到机械硬盘

### 10.1 三层内存的成本结构

| 内存层 | 持有成本（$/s）| 读取成本 | 完整覆盖时间 |
|--------|------------|--------|------------|
| **HBM** | 高（容量小）| 极快 | ~20ms |
| **DDR** | 中 | 快 | ~1-10s |
| **Flash/SSD** | 低 | 慢 | ~分钟级 |
| **HDD** | 极低 | 极慢 | ~1小时 |

### 10.2 持有 vs 读取的最优平衡
最优策略：让**持有时间 ≈ 覆盖时间**（存储容量 / 带宽）

即：数据应该存在刚好能在你的使用时间窗口内被完整读写的内存层级。

### 10.3 从缓存保存时间推断内存层级
API 定价中 5 分钟 vs 1 小时的保存时间差异：
- **5 分钟** → HBM（~20ms 覆盖，5 分钟 >> 20ms）
- **1 小时** → DDR 或 Flash

实际上如果算一下，覆盖整个 HBM 需要约 20ms，覆盖整个 DDR 需要 1-10 秒，覆盖 Flash 需要分钟级，覆盖 HDD 需要 1 小时左右——这与 API 定价策略完全吻合。

### 10.4 为什么 KV Cache 不能无限积累
因为 HBM 容量有限，且 KV Cache 的持有成本 = 每 Token 字节数 × 占用比例 × GPU 成本。一旦 HBM 被不常用的 KV Cache 塞满，GPU 就无法用于新请求，必须等待清理或拒绝请求。

## 十一、密码学与大模型的深层类比

### 11.1 共同的信息混合机制
神经网络和密码协议都涉及**信息在所有输入间混合**：
- 密码协议：打乱输入，使结构无法辨认
- 神经网络：从看似随机的数据（DNA/蛋白质/文本）中提取高层结构

**目标相反**，但**机制相似**——都需要混合操作。

### 11.2 可逆网络：从密码学到神经网络
**Fenmenthalm 结构**（密码学构造）：
- 输入 X → 通过不可逆函数 F(X) → 与 Y 相加 → 输出
- 可逆：因为 X 还在输出里，直接读取；Y = Z - F(X)

这个密码学构造后来被引入神经网络（2017-18 年论文 **RevNet: Reversible Networks**），使得整个神经网络可逆，前向传播后可完全逆向执行。

**用途：训练**——可逆网络不需要存储中间激活值，反向传播时重新计算即可，节省大量内存。

## 十二、投资启示录

### 12.1 内存墙是持续的需求来源
- **HBM 带宽**是硬约束，每代提升有限
- SK Hynix、Micron（HBM 供应商）持续受益
- 高带宽内存封装（CoWoS）产能是算力扩展的真正瓶颈之一

### 12.2 推理优化的三个方向
1. **批处理**：成本可降低千倍（但用户需接受排队延迟）
2. **稀疏注意力**：减少 KV Cache，降低内存墙影响
3. **多层级缓存**：HBM/DDR/Flash 分层，降低 KV Cache 持有成本

### 12.3 模型公司的定价策略
- 从 API 定价可反推硬件成本结构（内存带宽 vs 算力占比）
- 快速模式（付 6x 得 2.5x）：溢价不随规模线性增长，边际收益递减
- 缓存定价差异（10 倍差）：内存层级间的套利空间

### 12.4 Scaling Law 尚未到头，但方向变了
- 模型规模扩展在等待硬件（单 rack 容量）
- 算法创新（MoE、稀疏注意力）补偿了一部分扩展放缓
- 过度训练 100 倍说明：当前前沿模型仍处于"用推理成本补贴训练"阶段

## 十三、技术术语对照表

| 术语 | 含义 |
|------|------|
| **Roofline Model** | 用带宽和算力两个约束上限分析性能的方法 |
| **Batch Size (B)** | 同时服务的用户/序列数量 |
| **KV Cache** | Key-Value 缓存，存储历史 Token 的注意力信息，避免重复计算 |
| **Pre-fill** | 输入处理阶段，一次性计算所有输入 Token 的注意力 |
| **Decode** | 生成阶段，逐 Token 输出，每步需重新加载全部权重 |
| **MoE (Mixture of Experts)** | 稀疏激活的专家模型，只激活部分专家参数 |
| **Expert Parallelism** | 把不同专家分配到不同 GPU 的并行策略 |
| **Pipeline Parallelism** | 按层切分到不同 GPU，串行执行 |
| **Memory Wall** | 内存带宽跟不上算力增长，内存成为瓶颈 |
| **Sparse Attention** | 稀疏注意力，不对所有历史 Token 做注意力计算 |
| **Sliding Window Attention** | 只关注最近 N 个 Token 的注意力机制 |
| **HBM (High Bandwidth Memory)** | 高带宽显存，GPU 直接使用 |
| **$F_{peak} / M_{bandwidth}$** | 算力/带宽比 ≈ 300（历代 GPU 稳定值）|
| **6NDF Formula** | 训练计算量 = 6 × 活跃参数 × 数据 Token 数 |
| **RevNet** | 可逆网络，用于节省训练内存 |
| **Fenmenthalm Structure** | 密码学可逆结构，后被引入神经网络 |
